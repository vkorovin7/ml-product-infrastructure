# ML Product Infrastructure

Учебный проект для настройки воспроизводимого Python-окружения и автоматических проверок.

## Установка и запуск

Требуются [uv](https://docs.astral.sh/uv/) и `make`. `uv` установит и выберет Python 3.12
при необходимости. Команды ниже рассчитаны на Unix (macOS или Linux). В Windows используйте
WSL с установленным дистрибутивом Linux.

```sh
make setup
make check
```

`make setup` устанавливает зафиксированные зависимости из `uv.lock` и подключает Git-хуки.
`make check` проверяет линтинг, форматирование и типы, не изменяя файлы. Для запуска примера:

```sh
uv run python scripts/debug_tools.py
```

## Структура

- `src/ml_product_infrastructure/` — пакет проекта.
- `scripts/` — небольшие служебные скрипты и пример для отладки проверок.
- `pyproject.toml` — метаданные проекта и конфигурация Ruff/mypy.
- `.pre-commit-config.yaml` — проверки перед каждым коммитом.

## Проверки перед коммитом

Настройте хуки командой `make setup`. Перед коммитом запускаются Ruff (линтинг и форматирование)
и mypy в строгом режиме. Те же проверки можно выполнить вручную командой `make check`.

## GitHub flow

Работайте в короткоживущих ветках от `main`, отправляйте изменения через pull request и
дожидайтесь успешного CI перед слиянием. Ветка `main` должна принимать изменения только через PR.

## Данные

Скопируйте пример конфигурации и поднимите RustFS вместе с автоматическим созданием бакета:

```sh
cp .env.example .env
make s3-up
```

S3 API доступен по адресу `http://localhost:9000`, веб-консоль — `http://localhost:9001`.
Учётные данные берутся из `.env`. Бакет `ml-datasets` хранится в именованном Docker volume
`rustfs_data`; `make s3-down` останавливает контейнеры, не удаляя данные.

Загрузите неизменённый официальный архив CIFAR-10, затем соберите и опубликуйте обработанный
датасет:

```sh
make ingest
make data
```

Pipeline скачивает архив из `raw/cifar-10-python.tar.gz`, сохраняет PNG и JSON-аннотации локально,
делит исходный train на 45 000 train и 5 000 val со seed `42`, считает статистики только по train и
выкладывает версию `processed/cifar10/v1/`. Для другой версии и разбиения задайте параметры, не
меняя код:

```sh
make data DATA_VERSION=v2 VALIDATION_SIZE=6000 SEED=123
```

`make data` состоит из отдельных CLI-модулей `fetch-cifar10-raw`, `convert-cifar10`,
`split-cifar10`, `stats-cifar10` и `publish-cifar10`; каждый можно запускать отдельно через
`uv run <command> --help`. Загрузчик архива запускается командой `make ingest` или
`uv run ingest-cifar10`. Повторная загрузка пропускает существующий raw-объект, а публикация
занятой версии завершается ошибкой — укажите новый `DATA_VERSION`.

После сборки в бакете будут `raw/cifar-10-python.tar.gz` и
`processed/cifar10/<version>/images/`, `annotations/{train,val,test}.json`, `stats.json` и
`manifest.json`. Manifest содержит размеры выборок, SHA-256 и размеры файлов метаданных, параметры
разбиения и Git-коммит сборки.

## Эксперименты

Воспроизводимый запуск состоит из MLflow Tracking Server, PostgreSQL для метаданных, RustFS для
артефактов и отдельного контейнера обучения. MLflow слушает `http://localhost:5000`; его метаданные
хранятся в volume `mlflow_db_data`, а артефакты — в отдельном S3-бакете `mlflow`. Бакеты `ml-datasets`
и `mlflow` автоматически создаются командой `create-bucket`. Секреты задаются в локальном `.env`;
файл не коммитится.

```sh
cp .env.example .env
make setup
make infra-up
make baseline
make experiments CONFIG=configs/grid.yaml
make infra-down
```

`make infra-up` собирает контейнеры и поднимает хранилище, PostgreSQL и MLflow. `make baseline`
запускает простой классификатор `Flatten + Linear` в эксперименте `cifar10-baseline`. `make
experiments` строит декартово произведение сетки и запускает шесть конфигураций CNN в одном
эксперименте MLflow; параметры задаются в `configs/grid.yaml` и `configs/simple_cnn.yaml`. Можно
поменять сетку или конфиг без изменения Python-кода. Все запуски выполняются контейнером `trainer`,
подключённым к одной Docker-сети с MLflow и RustFS. CIFAR-файлы скачиваются из указанного S3-префикса
в volume `training_data` и повторно используются между запусками.

После каждой эпохи скрипт считает loss, accuracy и macro-F1 на validation. Чекпоинт с наименьшим
validation loss восстанавливается перед финальной оценкой на test. MLflow сохраняет конфиг,
параметры, метрики по эпохам, время обучения, эпоху лучшего чекпоинта и CSV-матрицу ошибок на
validation. В RustFS публикуются `models/<experiment_name>/<run_name>/model.pt`, `config.yaml` и
`metrics.json`; test-метрики используются для итогового отчёта, а выбор конфигурации делается только
по validation loss.

### Результаты CIFAR-10

Выполненные значения фиксируются здесь после прогона baseline и сетки. Для выбора используется
минимальный validation loss; test указан только для выбранной конфигурации.

| Запуск | Конфигурация | Лучшая эпоха | Val loss | Val accuracy | Val macro-F1 | Test loss | Test accuracy | Test macro-F1 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Baseline | Linear, lr=0.001, batch=128 | 2 | 2.0390 | 0.3050 | 0.2921 | 2.0348 | 0.3179 | 0.3064 |
| Grid 1 | CNN, lr=0.003, batch=128 | 2 | 2.0719 | 0.2448 | 0.1948 | 2.0668 | 0.2460 | 0.1959 |
| Grid 2 | CNN, lr=0.003, batch=256 | 2 | 2.1484 | 0.2258 | 0.1654 | 2.1455 | 0.2264 | 0.1655 |
| Выбрана | Linear, lr=0.001, batch=128 | 2 | 2.0390 | 0.3050 | 0.2921 | 2.0348 | 0.3179 | 0.3064 |

Выбрана линейная модель baseline: её validation loss `2.0390` оказался ниже, чем у лучшего CNN из
сетки (`2.0719`), поэтому она остаётся предпочтительной по заданному критерию. Значения получены на
коротком CPU-прогоне с 2 048 train-примерами и двумя эпохами; test приведён только для итогового
сравнения и не участвовал в выборе.

**Карточка CIFAR-10.** Источник: [официальная страница CIFAR](https://www.cs.toronto.edu/~kriz/cifar.html).
60 000 RGB-изображений размером 32×32: 50 000 train и 10 000 test, десять классов — airplane,
automobile, bird, cat, deer, dog, frog, horse, ship, truck. Используется стратифицированное
разбиение 45 000/5 000/10 000. Изображения маленькие и имеют ограниченную детализацию; исходные
Python-файлы являются pickle и читаются только после загрузки официального архива из указанного
источника. Данные и производные файлы остаются вне Git.
